# Архитектурный план: движок, ангар, React и мультиплеер

## Цель

Сохранить GalaxyDemo как движок и редактор сцен. Использовать существующий React-проект только для авторизации, ангара и HTML-панелей. Трёхмерная сцена, модели кораблей и рендеринг остаются в GalaxyDemo. Backend проекта `C:\projects\Galaxy` предоставляет HTTP API, PostgreSQL и WebSocket. Для сетевых сцен сервер исполняет авторитетную симуляцию без WebGL.

Целевой пользовательский путь:

```text
загрузка приложения
  → единый загрузочный экран движка
  → авторизация React через API
  → загрузка профиля и данных ангара
  → WebGL-сцена scene-hangar и предпросмотр выбранного корабля
  → запуск выбранной игровой сцены
      ├─ локальная: симуляция в браузере
      └─ серверная: ввод по WebSocket, симуляция и столкновения на сервере
```

## Принятые архитектурные решения

1. **Одна страница приложения.** React не встраивается в JSON сцены и не работает в iframe. HTML-приложение создаёт WebGL canvas движка и root React-панелей; оба работают в одном документе.
2. **Единственный владелец 3D.** GalaxyDemo загружает `scene-hangar`, игровые сцены, модели и рисует их. Экран `SpaceScene` из React не переносится; React Three.js-превью заменяется вызовами API движка.
3. **React — UI приложения.** React отвечает за регистрацию/вход, ангар, главное меню и общие HTML-панели. Смена 3D-сцены не перезапускает React и не создаёт второе меню.
4. **Движок владеет загрузочным экраном.** React и движок сообщают о своих задачах единому координатору загрузки. У каждого запроса есть завершение и ошибка; ни один компонент не скрывает экран загрузки независимо.
5. **Серверная сцена не запускается URL-запросом.** `?scene=first-game` выбирает клиентский контент, но сервер загружает только сцены из доверенной конфигурации. Игровые процессы запускаются как службы/процессы и создают комнаты.
6. **Сервер авторитетен для сетевой симуляции.** Клиент отправляет команды управления, сервер проверяет ввод и рассчитывает физику, столкновения и игровые результаты. Клиент отображает подтверждённое состояние.
7. **База не участвует в игровом тике.** PostgreSQL хранит аккаунты, ангар, прогресс и долговечные результаты. Состояние активной комнаты живёт в памяти процесса симуляции и сохраняется в БД только по необходимости/событиям.

## Целевая схема развертывания

```text
Браузер
  единый app shell: React DOM + canvas движка
       │ HTTPS: вход, профиль, ангар, создание/подключение к сессии
       │ WSS: ввод игрока, подтверждения, snapshots и игровые события
       ▼
Публичный backend
  HTTP API ─ авторизация, профиль, ангар, matchmaking/session tickets
  WebSocket ─ аутентификация соединения и транспорт игровых сообщений
  headless engine runtime ─ комнаты, фиксированный tick, physics.step()
       │
       └── PostgreSQL: аккаунты и долговечные данные
```

Для первого релиза API и WebSocket могут оставаться в одном Node.js backend. Статические файлы React и движка можно отдавать с одного домена через reverse proxy: `/` — приложение, `/api/*` — backend API, `/ws` — WebSocket, `/editor/*` — редактор (при необходимости). Допустима и отдельная статика/CDN, но тогда явно настраиваются production API URL, CORS и `wss://` endpoint. Секреты БД и JWT хранятся только в окружении backend.

  public/js/network-client/       WebSocket client, input, snapshots, interpolation
  public/js/editor/               редактор сцен и сетевых свойств
  public/ui/                      статическая production-сборка React

Galaxy React client
  auth/                           регистрация, вход, сессия
  hangar/                         данные ангара и выбор корабля

Не копировать физику отдельно в backend: сервер и браузер должны использовать один модуль физики и согласованный контракт сцены. Для этого выделить движковые headless-модули в импортируемый пакет/общий workspace. Сохранить публичные фасады существующих модулей на время миграции. Не переносить всё в монорепозиторий до первой интеграции; сначала согласовать совместимые API и сборки. Если отдельные репозитории сохраняются, общий runtime должен иметь один версионируемый источник, а не ручные копии.

## Контракт React ↔ движок

Создать маленький типизированный `EngineBridge`, который движок регистрирует до монтирования React. Его выдавать React через Context. Bridge — единственная точка связи UI с runtime, без прямого доступа к глобальному состоянию игры или WebGL.

Минимальные команды:

```text
loadScene(sceneId, options?)
showHangarShip(assetKey)
setApplicationMode(auth | hangar | menu | game | pause)
setLoadingTask(taskId, label, progress?) / finishLoadingTask(taskId)
connectSession(sessionTicket)
sendInput(controls, sequence)
```

Минимальные события:

```text
engine:ready
scene:loading / scene:ready / scene:error
hangar:preview-ready / hangar:preview-error
game:connected / game:disconnected
game:snapshot / game:event
loading:state
```

Bridge должен быть асинхронным и возвращать явный результат/ошибку для команд. Подписки возвращают функцию отписки; при размонтировании React не остаются listeners. До готовности движка команды либо ожидают readiness promise, либо завершаются контролируемой ошибкой, но не теряются молча.

`showHangarShip` принимает разрешённый ключ ассета, а не произвольный путь. Backend возвращает идентификатор модели, а UI/каталог сопоставляет его с ключом модели движка. Перед запуском сетевой игры сервер снова проверяет владение кораблём и его состояние.

## Единый экран загрузки и меню

Загрузочный экран остаётся UI движка, который уже показывает прогресс и ошибку. Ввести `LoadingCoordinator` с именованными задачами: инициализация движка, проверка сессии, запрос ангара, загрузка `scene-hangar`, загрузка выбранной модели. Координатор агрегирует прогресс и закрывает экран только когда обязательные задачи завершены. Необязательные запросы должны быть явно помечены, чтобы не блокировать вход в игру.

React передаёт состояние своих задач в координатор, но не отображает второй независимый splash screen. Ошибка аутентификации показывается в форме входа; ошибка обязательной загрузки сцены/ресурса — через общий экран движка с возможностью повтора/возврата.

React владеет общим меню (главное, пауза, переход в ангар/игру). Движок передаёт события `pause`, `resume`, `scene-ready`; React отправляет соответствующие команды через bridge. Существующую HTML-паузу игры постепенно убрать или заменить React-панелями, чтобы не было двух конкурирующих меню. Игровой HUD, специфичный для симуляции, на первом этапе можно оставить в движке.

## Сцена ангара и предпросмотр

`scene-hangar` — обычный JSON-файл сцены движка: база/ангар, камеры, освещение, точка предпросмотра, окружение и вспомогательные объекты. Она не содержит React-компонентов и не загружает React. UI-манифест/приложение решает, какие панели React показывать поверх неё.

При выборе корабля:

1. React выбирает объект из полученного от API ангара и показывает его характеристики.
2. React получает/находит соответствующий разрешённый `assetKey` и вызывает `bridge.showHangarShip(assetKey)`.
3. Engine preview service загружает модель через общий asset cache, удаляет/заменяет предыдущую модель в точке предпросмотра и сообщает результат.
4. Серверный ответ остаётся источником данных по владению, характеристикам и цене; клиентский preview только отображает модель.

Начать с одного preview-слота/корабля в общей сцене, не создавать отдельный WebGL-контекст на каждую карточку. Если потребуется несколько одновременно видимых кораблей, позже добавить несколько preview-слотов в тот же renderer.

## Сетевые сцены и серверная физика

Добавить в формат сцены версионируемую конфигурацию сетевого режима, например:

```json
{
  "network": {
    "mode": "local",
    "tickRate": 60,
    "snapshotRate": 20,
    "maxPlayers": 16
  }
}
```

`mode` принимает `local` или `server-authoritative`. Объекты получают явную политику репликации/authority: какие сущности существуют на сервере, какие видны клиенту, кто владеет вводом. Не синхронизировать автоматически UI, локальные визуальные эффекты и декоративные данные. Редактор показывает эти настройки только для сетевого режима и валидирует их при сохранении.

Нужен headless scene builder: из JSON сцены создать runtime-сущности, тела и коллайдеры без `document`, canvas, `gl.js`, текстур и WebGL buffers. Сейчас `physics/world.js` и узкая фаза уже не зависят от WebGL; `scene-runtime.js` содержит GL-зависимые операции, поэтому его следует разделить на подготовку данных/runtime и клиентское создание mesh.

Серверная комната выполняет симуляцию с фиксированным шагом (первоначально 60 Hz с контролем отставания). PostgreSQL не вызывается из tick. Порядок систем зафиксировать и тестировать: принятие/валидация input → игровые команды → physics step/contact events → игровые правила → фиксация состояния → snapshots. На старте не делать физику и игровой runtime независимыми микросервисами.

Клиентский `main.js` должен иметь локальный и сетевой simulation adapter: локальный режим продолжает использовать текущую симуляцию; серверный режим отправляет ввод и получает состояние, не двигая авторитетные тела локально. Разрешены camera smoothing и визуальная интерполяция snapshots; prediction собственного корабля — отдельный поздний этап с reconciliation.

## WebSocket-протокол

Зафиксировать версионированные типы сообщений и лимиты. Базовый handshake: HTTPS API аутентифицирует пользователя и выдаёт короткоживущий одноразовый ticket на подключение; WebSocket использует ticket, а не долгоживущий JWT в query string. Сервер проверяет ticket, пользователя, комнату, разрешённость сцены и срок действия. Повторный join/подключение обрабатываются явно.

Минимальные сообщения:

```text
client → server: join(ticket, protocolVersion)
client → server: input(sequence, clientTick?, controls)
server → client: joined(sessionId, playerId, tickRate)
server → client: snapshot(serverTick, entities[])
server → client: event(serverTick, eventId, payload)
server → client: error(code, message)
```

Клиент не передаёт координаты, столкновения, попадания или урон как факты. Сервер проверяет допустимые поля, диапазоны, частоту и монотонность sequence; ограничивает размер сообщений и output backlog; выдаёт только данные комнаты. Snapshot должен включать номер серверного тика и идентификаторы сущностей. Позже добавить delta compression/interest management по измеренной нагрузке, не в первой версии.

## Авторизация и API

Существующие auth и hangar API Galaxy остаются ответственными за учётные записи и долговременные данные. React хранит только пользовательскую сессию; ключи БД доступны только backend. Для WebSocket использовать одноразовый session ticket, не передавать JWT в URL и не писать секреты в логи. Проверять Origin, срок/повторное использование ticket, лимиты регистрации/входа и размер/частоту сетевых сообщений.

API для игрового запуска должен позволять запросить сессию/комнату и получить ticket для конкретной разрешённой сцены. Сервер сам определяет сцену и корабль игрока по БД/конфигурации; произвольные sceneId, asset path, положение и статистику от клиента считать недоверенными. Торговые операции и сохранения выполнять транзакционно, как и сейчас.

## План реализации по этапам

### Этап 0. Зафиксировать контракты и исходное поведение

- Утвердить URL/раздачу статики, формат scene IDs, ключ модели и владение данными между engine и backend.
- Записать текущие команды запуска и тесты клиентской сборки, API, каталога и trade.
- Описать сценарии: вход, загрузка ангара, выбор разных кораблей, локальная сцена, сетевой запуск, отключение сети.

**Готово, если:** выбран единый origin/reverse proxy или задокументированы production origins; ID корабля однозначно сопоставляется с моделью движка.

### Этап 1. Ввести приложение-shell и bridge без мультиплеера

- Создать одну страницу с WebGL canvas и React root; настроить Vite build output под статический каталог движка.
- Инициализировать engine bootstrap и зарегистрировать typed bridge до монтирования React.
- Перенести auth/hangar/menu UI в root React этой страницы; не переносить Three.js `SpaceScene`.
- Сохранить существующий standalone dev режим React только как временный/опциональный путь до завершения миграции.

**Готово, если:** React UI и игра работают в одном документе и WebGL context; клиентский production build выдаёт статику; React может запросить engine readiness и сцену через bridge.

### Этап 2. Свести загрузку к одному экрану

- Вынести управление загрузочным экраном из глобального кода `main.js` в app-level loading coordinator.
- Подключить к нему загрузку React auth/session/hangar и ресурсов движка.
- Добавить отображение ошибок, retry и очистку задач при отмене/смене сцены.

**Готово, если:** загрузка старта, ангара и игровой сцены не создаёт второй splash; экран не исчезает до готовности обязательных задач и не остаётся навсегда при ошибке.

### Этап 3. Создать 3D-ангар

- Добавить `scene-hangar` с базой, камерой, preview slot и корректными collision/render настройками.
- Вынести в движке сервис предпросмотра корабля, повторно использующий asset cache.
- Заменить React Three.js `SpaceScene` и локальную 3D-галерею вызовами `showHangarShip`.
- Перевести главное/паузное меню на единые React HTML-панели; оставить engine gameplay HUD до отдельного решения.

**Готово, если:** выбранный в ангаре корабль отображается в WebGL сцене движка; повторные выборы корректно освобождают/переиспользуют ресурсы; React показывает серверные характеристики, а не вычисляет их самостоятельно.

### Этап 4. Вынести headless runtime

- Разделить scene data/runtime construction и WebGL mesh creation.
- Выделить общий пакет с контрактом сцены, physics shapes/world и нужными gameplay systems.
- Подключить его к backend как единственный источник серверной физики; обеспечить запуск Node без DOM/WebGL.
- Определить серверно-совместимый API скриптов и запретить серверным scripts импортировать browser-only APIs.

**Готово, если:** одна тестовая сцена создаёт одинаковые начальные body/коллайдеры в браузере и Node; физические unit tests запускаются headless; backend не импортирует `main.js`, renderer или React.

### Этап 5. Добавить режим сцены и комнаты

- Версионировать схему сцены и добавить `network.mode`, tick/snapshot rate, maxPlayers и репликационные правила.
- Добавить редакторские контролы и валидатор сцены/сетевых сущностей.
- Добавить серверную allowlist/config для сцен и manager комнат; не запускать процесс по HTTP-запросу.
- Добавить API создания/входа в комнату и выдачи одноразового WSS ticket.

**Готово, если:** локальная сцена не требует WS; сетевую сцену нельзя подключить, если сервер её не разрешил; room загружается без рендера.

### Этап 6. Авторитетная симуляция и протокол

- Заменить текущий демонстрационный `stepPlayer` интеграцией headless `PhysicsWorld` и scene systems.
- Перейти с отправки `move(x,z)` на sequence-numbered controls; валидировать команды на сервере.
- Добавить фиксированный tick, состояние комнаты, обработку disconnect/reconnect и snapshots.
- На клиенте реализовать interpolation buffer; запретить сетевому режиму локально изменять авторитетную позицию/результаты столкновений.
- Перенести запуск игры из ангара на получение session ticket и загрузку правильной сцены.

**Готово, если:** два браузера подключаются в одну комнату; один игрок не меняет чужую симуляцию; тесты показывают, что итоговое движение и contact events выдаёт сервер, а клиент только отправляет ввод.

### Этап 7. Публикация и эксплуатация

- Собрать React в статику и публиковать вместе с engine client assets; задать production API/WSS адреса без localhost fallback в production build.
- Настроить HTTPS/WSS reverse proxy, разрешённые origins, секреты окружения, PostgreSQL backups и миграции.
- Запускать API/WS и комнатный runtime как постоянно работающую службу с graceful shutdown и health endpoints.
- Добавить логи соединений/ошибок без паролей, JWT и session tickets; метрики tick duration, active rooms/players и dropped snapshots.

**Готово, если:** fresh deployment проходит вход → ангар → preview → комната → серверное движение; секреты не находятся в статике; после перезапуска API БД сохраняет аккаунт/ангар, а активные комнаты ожидаемо пересоздаются или восстанавливаются по выбранной политике.

## Проверки и критерии приёмки

- Существующие `npm test` движка, client `npm test`/`npm run build`, backend `npm run check` остаются зелёными.
- Добавить интеграционные проверки API auth/session и WebSocket handshake, неверного/истёкшего ticket, неправильной сцены, размера и частоты сообщений.
- Добавить headless tests для загрузки scene-hangar/game scene, генерации тел/коллайдеров, фиксированного тика, контактов и повторного подключения.
- Добавить UI smoke checks: React auth/hangar открыты поверх canvas; выбор корабля заменяет preview; единое меню доступно в ангаре и игре; общий загрузчик сообщает ошибку.
- Проверить ручной сценарий с двумя браузерными клиентами и отдельно локальную сцену без подключения к WS.

## Не делать в первой версии

- Не запускать игровой сервер HTTP-запросом `/server?scene=...`; не создавать отдельный игровой процесс на каждого посетителя.
- Не внедрять микросервисы, Redis, отдельный matchmaking cluster или сложную ECS до необходимости, подтверждённой нагрузкой.
- Не синхронизировать каждый декоративный объект и каждую запись кадра в PostgreSQL.
- Не добавлять rollback prediction, delta compression и interest management до базового корректного серверного тика и измерений.
- Не поддерживать параллельно два 3D preview/render pipelines (React Three.js и renderer движка) для одного и того же ангара.
